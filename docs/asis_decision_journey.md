# AS-IS 의사결정 여정과 To-Be 승인점 (Stage 0-G)

**작성일:** 2026-10-18 · **전제:** `decision_definition.md`의 가상 고객·[가정] 항목 · **범위:** 대상 결정 1건(경보 창별 조치 선택과 작업지시)의 예외 처리 경로

## 1. AS-IS 여정 — 공정 경보가 발생한 경우

| # | 단계 | 사람 | 시스템 | 소요시간 [가정] | 현재의 어려움 |
|---|---|---|---|---|---|
| 1 | **경보** | 운전원 | DCS 고정 임계치 경보, 경보 요약 화면 | 수 초 | 임계치 경보는 "어떤 변수가 선을 넘었다"만 알린다. 운전 조건이 바뀌면 같은 임계치가 과다 경보를 내고(KOSHA P-116의 alarm flood), 센서 자체의 이상과 공정 이상을 구분하지 않는다 |
| 2 | **데이터 확인** | 운전원 → 엔지니어 | 히스토리안 트렌드, P&ID, 계기 점검 이력 — 각각 다른 화면 | 10–20분 | **근거를 여러 화면에서 손으로 모은다.** 센서를 믿어도 되는지(데이터 품질)와 공정이 이상한지가 한 화면에 없다 |
| 3 | **원인 판단** | 엔지니어 | 없음(경험), 과거 사례 기억 | 10–20분 | 냉각수 온도인지 피드 조성인지 밸브 고착인지의 후보가 사람 머릿속에 있고, 확신 정도가 기록되지 않는다. 야간엔 호출 대기 |
| 4 | **조치안** | 엔지니어 | 절차서·기술지침 검색(파일 서버·포털) | 10–15분 | 지침의 어느 조항이 이 상황에 해당하는지 찾는 시간. 찾지 못하면 경험으로 조치 |
| 5 | **승인** | 엔지니어(기준 내) / 생산팀장(생산 영향) | 메일·구두 | 대기 0.5–2시간 | 승인 요청에 근거·대안·예상 영향이 정리돼 있지 않아 왕복이 생긴다 |
| 6 | **실행·추적** | 정비팀 | CMMS 작업지시 | 수 분(작성) | 작업지시와 "그때의 경보·판단 근거"가 연결되지 않아 사후에 오탐이었는지 알 수 없다 |

합계 [가정]: 경보 1건당 엔지니어 30–55분 + 승인 대기. 경보 폭주 시에는 건별 처리가 불가능하다.

**업무 공백(계획서 §2.1)의 위치:** 2단계(센서 신뢰 여부 + 공정 이상 여부를 한 번에 보는 근거 묶음), 4단계(조항 검색·인용), 6단계(결정–근거–결과의 연결). 1단계는 DCS가 이미 하지만 "확신 정도 없는 임계치"라는 점이 2·3단계 부담의 원인이다.

## 2. To-Be 여정 — 공정 신뢰성 에이전트 (L1 조언형 → L2 승인형)

| # | 단계 | To-Be 수행 주체 | 에이전트가 하는 일 ("수행" = 사람 대신 작업을 준비함, 결정이 아님) | 사람이 유지하는 것 |
|---|---|---|---|---|
| 1 | 경보 | 에이전트 (`gate_check` → `detect_diagnose` Skill) | 품질 게이트 통과 창에만 탐지 적용. 경보에 conformal p-value(BH 통과 여부)와 "센서를 믿어도 되는 창인가"(PASS/FLAG/BLOCK)를 붙인다. BLOCK이면 "판단 불가"로 알림 | 게이트 임계·α의 설정(사전등록 값) |
| 2 | 데이터 확인 | **에이전트** | 창의 변수 요약, 게이트 상태, p-value, 분기 센서(SHAP 기여)를 한 묶음으로. **수행 1순위** | 어떤 센서·문서를 볼 권한이 있는가(ACL) |
| 3 | 원인 판단 | 에이전트 후보, 사람 확정 | 결함 유형 **conformal set**(크기 = 불확실성 척도)과 기여 센서 제시. 집합 크기 1이면 확신, 크면 "추가 조회" 쪽으로 정책이 기운다(H1 3신호) | 원인 확정. 집합은 후보이지 결론이 아님 |
| 4 | 조치안 | 에이전트 (`retrieve` Skill) | 결함→지침 매핑(`fault_to_guidance_map.md`, 가정)으로 조항 후보 → ACL 사전 필터 → 하이브리드 검색 → 리랭커 → **인용 조항과 함께** 조치안 초안. 조항이 없으면 조치안을 내지 않고 보류(H3). **수행 2순위** | 매핑 규칙의 승인(가정임을 인지) |
| 5 | 승인 | **사람** | 승인 요청서 자동 생성: p-value·집합·조항 인용·예상 조치. `interrupt()`로 정지 → 승인/수정/거부 → 재개(0-D 검증). | **승인점 ①** 공정 엔지니어: 모든 조치안(L1). **승인점 ②** L2에서 예외만(낮은 p·단일 집합·근거성 통과 조건 미달) |
| 6 | 실행·추적 | 사람 실행(정비), 에이전트 추적 | mock CMMS에 작업지시 발행(승인 후에만), `mart.work_orders`·`mart.approvals`·`mart.evidence`로 경보–판단–근거–결과 연결. **수행 3순위** | 실행 확정·롤백 |

**L1과 L2의 차이는 5단계 하나다.** L1은 모든 조치안이 승인점 ①을 거친다. L2는 세 조건(낮은 p-value·단일 원소 진단 집합·근거성 통과)을 모두 만족하는 조치안만 자동 발행하고 예외만 승인점 ②로 올린다. 승격 규칙은 리플레이로만 평가(Should). L3(운전 조건 변경)는 어느 단계에서도 하지 않는다.

**사람이 끝까지 유지하는 세 가지:** 설정값·권한·매핑 규칙(입력 측), 승인(결정 측), 실행과 롤백(출력 측). 에이전트는 "게이트 → 탐지·진단 → 근거 검색 → 요청서" 구간을 맡는다.

## 3. 기대 변화 (측정 단위, 계획서 §4.7·§5.2 계산 경계)

| 지표 | AS-IS [가정] | To-Be 목표 | 보고 방식 |
|---|---|---|---|
| 경보 1건 처리 시간 | 30–55분 | 2·4단계 자동화로 10–20분 | 처리 능력으로 보고, 인건비 환산 없음 |
| 행동 비용(오탐 작업지시·미제안 지연·보류·조회) | B1·B2 기준선 | 3신호 정책 < B1·B2, 쌍별 CI | H1, 상대 계수 |
| 실현 FDR | 임계치 경보엔 정의 없음 | ≤ 0.10(교환가능 가정) | H2, 분포 변화 시 초과를 결과로 보고 |
| 근거 추적성 | 조항 인용 없음 | citation hit@3, 근거 없는 조치안 0 | H3, 공학적 타당성은 판정 안 함 |
| 승인 왕복 | 1–2회 | 요청서 표준화로 감소 | 파일럿 관찰 항목(시뮬레이션 밖) |
| 알람→조치안 latency, 토큰·비용 | 해당 없음 | 측정 시작 | 선행 지표, 선행성 미검증 |

## 4. 이 여정이 답하지 않는 것

실제 운전원·엔지니어의 행동(채택률·수정 빈도·요청서를 읽는 시간)은 가상 고객에서 관측할 수 없다. 1·3·4단계는 리플레이와 평가셋으로, 2·5·6단계는 구현 여부·latency·결정론으로만 평가한다. TEP에 없는 비결함 변동(계획 정비·센서 교체·생산량 변경)에서의 오탐은 본 프로젝트가 측정하지 못하며, 실제 고객이면 파일럿 첫 4주의 관찰 항목이 된다.
